# voice-intent-pragmatics-bench

음성 대화 서비스에서 **빠르면서도 사용자의 실제 의도를 정확히 파악하는 방법**을 찾기 위한 실측 벤치마크입니다. 한국어 음성 발화 30문항을 화용론(말이 상황 속에서 하는 일을 다루는 언어학) 기준으로 만들고, 모델·설정·방법별로 **첫 발화까지 지연**과 **의도 파악 정확도**를 함께 잽니다.

## 결과

측정: 2026-10-26~27, 한국에서 각 사 공개 API 호출. 음성은 쓰지 않고, 음성이 인식되어 텍스트 메시지로 왔다고 가정합니다. 37개 조건 × 30문항 × 3회 = 3,330회 응답(오류 0), 별도로 지연 대조군 630회. 채점: `claude-opus-5-5` 블라인드, 응답 3,330건 + 화용 분석 630건. 4차 선별은 별도로 240회 응답 + 240건 채점, 지연 대조군 48회. 5차 탐색은 추정 생성 146회(응답용 30회 + 시간 재측정 30회 + 원인 분석 38회 + 관점 2개 48회) + 응답 880회(지연 대조 184회 포함) + 채점 876건(추정 180건 포함). 6차 여행은 추정·목표 생성 44회 + 응답 360회 + 지연 대조 120회 + 채점 400건(추정 40건 포함) + Jev 게이트 요청 420회(점검·순서 검사·맥락 게이트 포함; 버그가 있던 첫 버전의 요청 159회와 그 점수로 돌린 응답 80회는 집계에서 뺌).

### 빠른 설정 + 화용 정보로 상위 모델에 얼마나 다가가나 (2차)

질문: 추론 강도가 낮거나 작은 모델에 화용 정보를 주면, 지연은 그대로 두고 더 강한 모델(Gemini 3.8 Flash 기본, 95.0%, 첫 발화 2.0초)의 정확도에 가까워지는가? 추가 호출이 없는 방법만 씁니다: A4 화용 점검표, C 공유 맥락(사용자 프로필 + 최근 기기·일정 기록), C+A4.

![빠른 설정에서 상위 모델까지](results/gap_to_strong_model.png)

1. **공유 맥락은 지연을 거의 늘리지 않고 빠른 설정의 정확도를 올렸습니다.** 빠른 설정 4개 합산 +3.9%p (−0.3~+9.2), 부트스트랩의 96% 가 개선 쪽이고, 첫 발화 변화는 같은 실행의 대조군 대비 +11ms 입니다. 8개 조합 모두 첫 발화 변화가 −46~+29ms 였습니다.
2. **Mercury 3 기본 + 맥락+점검표: 93.9%, 첫 발화 823ms.** 상위 모델과의 정확도 격차 중 82% 를 메웠고, 남은 차이는 −1.1%p (−10.0~+5.6) 입니다. 첫 발화는 약 2.5배 빠르고, 1,000턴당 비용은 $0.15 로 상위 모델($0.28)의 약 절반입니다.
3. **GPT-6 Luna + 공유 맥락은 +6.1%p (+0.6~+12.2) 로, 2차 실험에서 신뢰구간이 0 을 벗어난 유일한 개선입니다.** 맥락+점검표는 92.8% (+7.2%p, 격차의 77%) 였습니다.
4. **효과는 모델에 따라 다릅니다.** 기준 정확도가 이미 높은 Gemini 3.5 Flash-Lite(90.6%)는 +1.1%p / −1.1%p 로 거의 변하지 않았습니다. Mercury 3 instant 는 맥락으로 +3.9%p(격차의 41%) 올랐지만 점검표를 더하면 오히려 낮아졌습니다(88.3%).
5. **맥락이 점검표보다 일관됩니다.** 맥락에 점검표를 더한 효과는 Mercury 3 +0.6%p, Luna +1.1%p, Mercury 3 instant −1.1%p, Gemini 3.5 Flash-Lite −2.3%p 로 엇갈렸습니다. 모델이 이미 하는 추론을 지시하는 것보다, 모델이 모르는 사실(관계, 일정, 기기 기록)을 주는 쪽이 효과가 컸습니다.
6. **지연은 같은 시간대끼리 비교해야 합니다.** 같은 기준 설정의 첫 발화 중앙값이 1차 실행과 2차 실행 사이에 Gemini 3.5 Flash-Lite 628 → 972ms, Luna 851 → 970ms 로 바뀌었습니다. 방법이 만든 지연 차이(±50ms)보다 시간대 차이가 훨씬 큽니다.
7. **주의.** 상위 모델과의 차이가 0 을 포함한다는 것은 "같다"는 증명이 아닙니다(30문항으로는 차이 구간이 ±8%p 안팎). 맥락 기록은 정답을 아는 작성자가 골라 효과가 낙관적일 수 있고, 상위 모델에는 같은 맥락을 주지 않았습니다. 억양 정보(한숨, 강세 등)는 실제 메시지에 없으므로 조건에서 뺐습니다.

### 맥락을 사람이 고르지 않으면 (3차)

2차의 공유 맥락(C)은 정답을 아는 작성자가 관련 사실 1~2줄을 골라 넣은 것입니다. 3차는 사람의 선별을 뺍니다. **C-auto** 는 관련 사실을 관련 없는 기록 10개 사이에 섞은 로그를 그대로 주고, **C-auto+H** 는 여기에 상위 모델(Gemini 3.8 Flash)이 사용자가 말하기 전에 로그·기기 상태·직전 대화만 보고 미리 만든 추정 최대 5개(확신도 포함, "사실이 아님" 표시)를 더합니다. 추정 생성기는 사용자 발화와 정답을 보지 않습니다.

![사람이 고르지 않은 맥락과 자동 가설](results/gap_auto_context.png)

1. **사람이 고르지 않은 로그만 주면 효과가 줄었습니다.** 같은 3개 설정에서 손으로 고른 맥락은 평균 +4.8%p, 선별 없는 로그는 합산 +2.6%p (−1.3~+6.7) 였습니다. 반어는 기준보다 낮아졌습니다(70.4 → 64.8%). 반어의 근거인 "수면 음악을 요청했는데 헤비메탈 168 BPM 재생 중" 같은 사실이 잡음 속에 묻히면, 기대와 상황의 어긋남을 놓칩니다.
2. **발화 전에 미리 만든 추정을 더하면 이 리포에서 가장 큰 개선이 나왔습니다.** 3개 설정 합산 +8.0%p (+3.9~+12.6), 부트스트랩의 100% 가 개선 쪽이고 첫 발화 변화는 −4ms 입니다. 세 설정 모두 개별 신뢰구간이 0 을 벗어났습니다: Mercury 3 instant +7.8%p, Mercury 3 +7.2%p, GPT-6 Luna +8.9%p.
3. **Mercury 3 기본 + 자동 가설: 96.1%, 첫 발화 844ms.** 상위 모델 기본 설정(95.0%, 2,020ms)과의 차이는 +1.1%p (−5.0~+6.7) 이고, 의도 이해율은 96.7% 로 같습니다.
4. **추정이 효과를 낸 현상**: 선별 없는 로그 대비 반어 64.8 → 90.7%, 자기 수정 83.3 → 96.3%, 높임법 77.8 → 83.3%. 걱정했던 과잉 행동은 없었습니다. "아 오늘 진짜 하루 길었다" 문항에는 "조명·냉난방 제어를 요청할 가능성 0.8" 같은 추정이 들어갔지만, 감정·혼잣말 정확도는 100% 였고 과잉 행동 판정은 0건이었습니다.
5. **추정이 답을 미리 알려 줘서 생긴 효과만은 아닙니다.** 추정 목록이 정답 의도를 그대로 담은 문항은 30개 중 9개였고, 부분적으로 담은 문항 11개, 전혀 담지 않은 문항 10개였습니다(분석 채점기로 대조). 효과는 세 묶음에서 비슷했습니다: 정답 명시 +9.3%p, 부분 포함 +7.1%p, 정답 없음 +7.8%p (0.0~18.3). 정답을 담지 않은 추정도 도움이 된 것은, 추정이 잡음 섞인 로그에서 관련 사실을 짚어 주는 역할을 했기 때문으로 보입니다 (가설).
6. **미리 계산할 수 있는 문항만 봐도 효과가 남습니다.** 직전 비서 발화가 있는 11개 문항은 비서가 말한 뒤에야 추정을 만들 수 있어, 아래 생성 시간으로는 대개 늦습니다. 상태만으로 미리 만들 수 있는 19개 문항의 효과는 +7.3%p (+2.6~+13.2) 였습니다.

7. **대가는 비용과 생성 시간입니다.** 상위 모델이 매 턴 추정을 만들면 1,000턴당 $3.32 가 더 들어, 응답 모델을 합쳐 $3.41~$3.49 입니다. 상위 모델에 바로 답하게 하는 것($0.28)의 약 12배입니다. 생성 시간은 중앙값 7.6초, 상위 10% 9.6초라, 사용자가 비서의 말이 끝나고 몇 초 안에 다시 말하면 추정이 준비되지 않습니다. 실제로는 상태가 바뀔 때만 비동기로 생성하거나, 더 싼 생성 모델을 쓰거나, 출력을 줄여야 합니다 (가설). 더 싼 생성 모델은 5차에서 일부 확인했습니다. Mercury 3 instant 가 1.1초, 1,000턴당 $0.21 로 만든 추정(v2 프롬프트)을 instant 응답에 넣자, 24문항에서 상위 모델 추정과 정확도 차이를 가를 수 없었습니다. 다만 같은 추정을 GPT-6 Luna none 응답에 넣었을 때는 효과가 없었고, 상위 모델 추정보다 5.6%p 낮았습니다(−12.5~1.0). 상태가 바뀔 때만 생성하는 방식은 시험하지 않았습니다.
8. **해석.** 효과의 출처는 상위 모델이 미리 해 둔 상황 해석입니다. 단, 추정이 사용자가 말하기 전에 준비되어 있을 때의 이야기입니다. 빠른 모델이 스스로 화용 추론을 더 하게 한 방법(점검표, effort 상향)은 효과가 작았지만, 강한 모델이 발화 전에 상황을 해석해 둔 결과를 빠른 모델에 주자 상위 모델 수준에 도달했습니다. 정확도와 응답 속도는 분리할 수 있었지만, 비용은 분리되지 않았습니다.
9. **주의.** 문항의 상태와 로그는 시나리오에 맞춰 쓴 것이라 실제 로그보다 "다음에 일어날 일"을 추정하기 쉽습니다. 추정 생성기가 목표선과 같은 Gemini 3.8 Flash 라는 점, 30문항으로는 상위 모델과 같다는 것을 증명할 수 없다는 점도 함께 봐야 합니다.

1. **상위 방법 사이의 차이는 대부분 정답 기준에 논란이 있는 3문항에서 나왔습니다.** 3문항은 REP-01, HON-01, QFR-02 이며, 논란 내용은 아래 "채점 검수"에 있습니다. 이 3문항을 빼면(21문항) Mercury 3 기본이 이미 93.7%, 로그만 준 C-auto 가 96.0% 로 Gemini 3.8 Flash(96.0%)와 같습니다. 방법 사이의 차이도 1~2문항입니다: M5·M5b·M8 100%, M4·M7 97.6%. 이번 선별 문항은 Mercury 3 기본 위에서 상위 방법끼리 순위를 가릴 만큼 어렵지 않았습니다.
2. **M5 (미리 만든 후보 중 "이 의도라면 이렇게 말했을까"로 고르기): 24문항 97.9%, 21문항 100%.** 같은 상황 10개를 "참고하라"며 준 M1 은 21문항에서도 92.9% 라, 지시 방식의 차이는 논란 문항을 빼도 남습니다. 반면 싼 모델(Mercury 3 low) 후보를 넣은 M5b 와는 21문항에서 같아(둘 다 100%), "강한 모델 후보라야 효과가 있다"는 이번 데이터로는 확인되지 않습니다. 말하는 중 빠른 모델(Mercury 3 instant) 후보를 넣은 M5c 는 논란 없는 문항(IMP-02, IMP-03, MUL-01)에서도 떨어져 21문항 90.5% 로 기본보다 낮았습니다. 후보가 빗나가면 고르기 지시가 오히려 해가 될 수 있습니다.
3. **M4 (답할 때 해석 3~5개를 숨겨 쓴 뒤 골라 답하기): 95.8%, 21문항 97.6%.** 미리 계산할 것이 없고 1,000턴당 $0.27 입니다. 대신 해석을 쓰는 동안 첫 발화가 +609ms 늦어집니다. 형식 실패 1건.
4. **해석을 10개로 늘린 M7 은 정확도는 그대로이고 속도만 잃었습니다.** 21문항에서 M4 와 같은 97.6% 이고(점수가 다른 문항은 논란 문항 HON-01 하나), 첫 발화는 +1,066ms 로 M4 의 약 두 배입니다. 숨겨 쓰는 해석이 길어진 만큼(추론 제외 출력 p50 134 → 225토큰, 추론 토큰 329 → 454) 기다리는 시간이 늘었습니다. 해석을 쓰지 않고 바로 답한 형식 실패가 2건 있었습니다(들리는 말에 해석이 섞이지는 않음).
5. **속으로만 해석 10개를 떠올리게 한 M8 은 계산을 늘리지 않았습니다.** 추론 토큰이 같은 시각 대조군과 같고(p50 168 대 182) 첫 발화도 그대로입니다(-12ms). 24문항 91.7% 는 로그만 준 C-auto(91.0%) 대비 +0.7%p 이고, 감점은 모두 논란 3문항에서 나와 21문항에서는 100% 입니다. 지시 덕분에 나아졌는지는 C-auto(21문항 96.0%)와 1~2문항 차이라 가릴 수 없습니다.
6. **보류: M3 (로그를 관련 사실 요약으로 다시 쓰기), M6 (발화 앞 절반으로 가설).** 둘 다 91.7% 로 선별 없는 로그(91.0%)와 거의 같았습니다. 생성이 빠르고(1.9초, 1.2초) 싸지만($0.51, $0.36) 이번 선별에서는 이득이 보이지 않았습니다. M6 생성이 빠른 이유는 Mercury 3 instant 가 생각 토큰 없이 출력 약 320토큰만 쓰기 때문입니다(M1 은 생각 약 1,200 + 출력 약 700토큰을 초당 약 100토큰으로 생성). 다만 1.2초라도 사용자가 말을 마치기 전에 끝난다는 보장은 없습니다. 발화 뒤 절반은 0~14음절이라, 초당 5~7음절로 말한다고 가정하면 말이 끝나기 전에 생성이 끝나는 문항은 24개 중 7~11개입니다. 말이 끝난 뒤 끝을 감지하는 대기 500ms 를 더해야 15~18개가 됩니다(발화 속도와 대기 시간은 가정값이며 측정하지 않았습니다).
7. **탈락: M1·M2 (발화 전 상황 10개).** 강한 모델이 만든 10개(91.7%)는 3차의 5개(95.1%)보다 낮았고, 싼 모델이 만든 10개(87.5%)는 로그만 줬을 때(91.0%)보다도 낮았습니다. 상황을 많이 유추시키면 겹치거나 빗나간 추정이 늘어 오히려 방해가 됩니다. 해석을 여러 개 만들면 서로 비슷해진다는 선행 연구([2505.11679](https://arxiv.org/abs/2505.11679))의 경고와 같은 방향입니다.
8. **주의.** 1회 측정·24문항이라 점마다 ±10%p 안팎의 불확실성이 있어, 5%p 안쪽의 차이로는 순위를 정할 수 없습니다. 첫 발화 변화도 24회의 중앙값이라 ±100ms 정도는 흔들립니다. Mercury 3 기본은 논란 없는 문항에서 이미 상위 모델과 같아서, 방법의 효과를 가리려면 더 약한 응답 모델(Mercury 3 instant, Luna none: C-auto 21문항 90.5%)이나 더 어려운 문항이 필요합니다.

### 같은 모델이 추정을 만들면 (5차, 10문항 탐색)

응답 모델이 미리 만든 추정(자기 추정)이 도움이 되는지, 그리고 GPT-6 Luna 의 none 과 low 가 얼마나 다른지 봤습니다. 이어서 Mercury 3 medium 응답에 같은 Mercury 3 를 생각 없이(instant) 돌려 만든 추정을 넣는 조건도 시험했습니다. 이 실험은 두 단계로 나뉘므로 표도 단계별로 나눴습니다.

- **추정 생성**: 사용자가 말하기 전에 응답할 모델이 직접 "사용자가 다음에 원할 만한 것"을 5개 이내의 JSON 목록으로 만드는 별도 호출입니다. 사용자 발화와 정답은 보지 않습니다. 재는 것은 생성 시간, 생성 실패, 추정 적중입니다.
- **응답**: 사용자가 말한 뒤 비서가 하는 대답입니다. 시스템 프롬프트에 로그만 넣거나, 로그 아래에 자기 추정을 덧붙입니다. 로그는 관련 기록이 관련 없는 기록 10개 사이에 섞인 것입니다. 재는 것은 응답 정확도, 첫 발화 시간, 잘못된 행동입니다.
- **용어**:
  - 응답 정확도: 응답이 사용자의 의도대로 처리했는지 채점한 값입니다(0·1·2점 평균을 %로).
  - 추정 적중: 미리 만든 추정 목록이 실제 의도를 담았는지 채점한 값입니다(0·1·2점).
  - 생성 실패: 추정 생성 호출이 프로그램이 읽을 수 있는 목록을 돌려주지 않은 경우입니다. 다시 요청해서 모든 문항의 추정을 확보했습니다.
- **문항**: 포화되지 않은 화용 범주마다 1문항씩 10문항 × 2회입니다.
  - 자기 수정은 정답 기준에 논란이 있는 REP-01 대신 REP-02 를 썼습니다.
  - 높임법은 문항이 HON-01 하나뿐이라 그대로 두었습니다.
  - 응답에 쓰는 추정은 1회째 생성물로 고정했고, 2회째에는 생성 시간과 실패만 다시 쟀습니다.
  - instant 추정 조건은 나중에 따로 돌렸습니다. 첫 발화는 그때 같은 실행에서 다시 잰 로그만·medium 자기 추정 조건(채점 안 함)과 D 표에서 비교합니다.
  - Gemini 3.8 Flash 추정 조건도 같은 실행에서 돌렸지만 이 절에서는 뺐습니다(원본은 `results/selfhyp/`).

4. **instant 추정은 빨랐지만 응답을 낫게 하지 않았습니다.** Mercury 3 medium 응답에 넣었을 때 응답 정확도는 90.0% 로, 로그만(95.0%)보다 1건 낮고(-5.0%p, -12.5~0.0) medium 자기 추정(100%)보다 2건 낮았습니다. 감점 3건은 다음과 같습니다.
   - MUL-01: 우산 알림을 빠뜨렸습니다. 로그만 조건에도 같은 실수가 1건 있었습니다.
   - HON-01: 할머니께 전화로 할지 문자로 할지 되물었습니다.
   - POL-01: 식당을 추천하지 않고 "잠시만요"로 끝냈습니다.

   이 3문항의 instant 추정 목록에는 배터리, 공기청정기 필터, 택배처럼 로그의 관련 없는 기록에서 나온 추정이 섞여 있었습니다. 다만 추정 적중 점수는 instant 0.40, medium 0.35 로 비슷해서, 적중 점수만으로는 이 차이가 보이지 않습니다. 같은 instant 추정을 더 약한 instant 응답에 넣었을 때는 정확도가 올랐고, GPT-6 Luna none 응답에서는 오르지 않았습니다(아래 "약한 응답 설정에 넣으면").
5. **이 10문항에서 로그만보다 응답이 좋았던 것은 느린 medium 자기 추정뿐이었습니다(+5.0%p, 1건 차이).** 생각을 줄여 추정을 빠르게 만들면(6.9 → 1.2초) 그 이득이 사라졌습니다. 표본이 작아 확정할 수는 없습니다.
6. **추정을 붙였을 때 첫 발화가 늘어나는지는 측정마다 달랐습니다.** medium 자기 추정은 로그만 대비 1회째 +496ms, 2회째 -189ms, D 표 +310ms 였고, instant 추정은 D 표에서 +39ms 였습니다. 표본이 작아 판단하기 어렵습니다.
7. **Luna low 는 자기 추정을 붙여도 나아지지 않았습니다 (92.5 → 90.0%).** 자기 추정 조건의 감점 4건 중 3건은 의도는 맞히고 행동을 거절한 응답입니다. 예를 들어 할머니께 보낼 말을 "저녁 드셨어요?"로 바꿔 놓고 "지금은 문자를 보낼 수 없어요"라고 답했습니다.
8. **응답 정확도 차이는 모두 응답 1~3건이라 이 표본으로는 확정할 수 없습니다.** 확실한 결과는 시간과 실패입니다. 잘못된 행동은 모든 조건에서 0건입니다.

#### 원인 분석: 추정이 왜 응답을 더 낫게 만들지 못했나

추정의 질이 낮았던 이유가 **소스(생성기에 준 정보)가 부족해서인지**, **추정을 만드는 프롬프트가 부족해서인지** 나눠 봤습니다. 응답 정확도 차이는 응답 1~3건이라 원인을 따질 수 없어서, 여유가 있는 추정 단계(추정 적중 0.35~0.60)에서 봤습니다. "잡음 추정"은 로그의 관련 없는 기록(배터리, 택배, 공기청정기 필터 등)에서만 나온 추정입니다. 추정 문장과 기록의 낱말을 맞춰 센 근사치입니다.

**원래 프롬프트(v1)로 만든 추정의 출처 (본 10문항)**

| 생성 모델·설정 | 추정 수 (문항당) | 잡음 추정 비율 | 관련 기록을 짚은 문항 |
|---|---|---|---|
| Mercury 3 medium | 50 (5.0) | 48% | 9/10 |
| Mercury 3 instant | 50 (5.0) | 62% | 10/10 |
| GPT-6 Luna low | 39 (3.9) | 38% | 9/10 |

**프롬프트 v1 대 v2 (Mercury 3 instant)**

원래 프롬프트(v1)와, 관련성 기준을 넣고 0~5개를 허용한 프롬프트(v2) 비교. v2 는 본 10문항의 결과를 보고 고쳤으므로, 못 본 14문항이 공정한 비교입니다. 잡음 추정은 관련 없는 기록에서만 나온 추정이며 키워드 대조로 센 근사치입니다.

| 프롬프트 | 문항 | 추정 수 (문항당) | 잡음 추정 비율 | 관련 기록을 짚은 문항 | 추정 적중 (0~2) |
|---|---|---|---|---|---|
| v1 | 본 10문항 | 50 (5.0) | 62% | 10/10 | 0.40 |
| v1 | 못 본 14문항 | 70 (5.0) | 56% | 11/14 | 0.57 |
| v2 | 본 10문항 | 39 (3.9) | 33% | 9/10 | 0.50 |
| v2 | 못 본 14문항 | 55 (3.9) | 31% | 13/14 | 0.93 |

1. **소스는 부족하지 않았습니다.** 10문항 모두 의도를 짐작하는 데 필요한 관련 기록(1~2개)이 로그에 있었고, 생성기는 9~10문항에서 그 기록을 실제로 짚었습니다. 할머니가 높임말 대상이라는 관계 정보도 프로필로 들어갔습니다. 다만 HON-01 에서 이를 쓴 생성기는 없었습니다.
2. **소스에 잡음이 많고, 프롬프트가 잡음을 걸러내지 못하게 했습니다.** 관련 기록은 문항당 1~2개인데 잡음 기록은 약 10개입니다. 원래 프롬프트는 "최대 5개"라고만 해서 Mercury 는 모든 문항에서 5개를 꽉 채웠습니다. 관련 기록을 쓰고 남은 자리는 잡음 기록으로 채워져 잡음 추정이 절반 안팎(medium 48%, instant 62%)이었습니다. 추정을 적게 낸 Luna low(문항당 3.9개)가 잡음 비율이 가장 낮았습니다(38%). 생각을 끈 instant 가 잡음을 가장 많이 썼습니다.
3. **프롬프트를 두 군데만 고치자 추정이 나아졌습니다 (v2).** 고친 점은 (1) "현재 상태·시각·직전 대화와 직접 이어지지 않는 기록은 쓰지 않는다" (2) "0~5개, 없으면 빈 목록"입니다. 관점(축)은 더하지 않았습니다. Mercury instant 기준으로 잡음 추정이 62 → 33% (본 10문항), 56 → 31% (못 본 14문항)로 줄었습니다. 못 본 14문항의 추정 적중은 0.57 → 0.93 (+0.36, 95% CI +0.14~+0.64) 으로, 6문항이 나아지고 나빠진 문항은 없었습니다. 본 10문항은 0.40 → 0.50 (CI 가 0 을 포함) 입니다. 생성 실패는 두 프롬프트 모두 0건이었고, 같은 v1 추정을 세 번 채점했을 때 점수는 모두 같았습니다.
4. **프롬프트로도 넘을 수 없는 한계가 있습니다 (판단).** 24문항 중 10문항은 v1·v2 모두 추정 적중 0점이었습니다. 대부분 의도가 발화 안에만 있는 문항입니다. 자기 수정(REP-01·02·03), 짧은 생략(ELL-02 "아니 좀 더", ELL-03 "아빠한테도"), 단답(AMB-02 "됐어 됐어"), 발화에서 처음 나오는 이유(IMP-01 "민수 다이어트")가 그렇습니다. 사용자가 말하기 전에 만드는 추정은 이런 의도를 담을 수 없고, 그 문항에서는 응답 모델이 발화를 직접 해석해야 합니다.
5. **응답에 넣었을 때의 효과는 아래 후속 시험에서 쟀습니다.** 추정은 나아졌지만 응답 정확도는 달라지지 않았습니다.

#### 원인 분석 후속: 고친 추정을 응답에 넣으면 (못 본 14문항)

v1·v2 프롬프트로 Mercury 3 instant 가 만든 추정을 Mercury 3 medium 응답에 넣었습니다. 로그만 준 조건과 같은 실행에서 비교했고, 추정을 고칠 때 보지 않은 14문항 × 2회입니다.

Mercury 3 medium 응답, 못 본 14문항 × 2회 (AMB-02, AMB-03, ELL-02, ELL-03, IMP-02, IMP-03, PHA-02, POL-02, QFR-02, QFR-03, REP-01, REP-03, SAR-02, SAR-03), 세 조건을 같은 실행에서 잼. 추정은 Mercury 3 instant 가 만들었고 응답할 때 로그 아래에 덧붙임. 정답 기준에 논란이 있는 QFR-02·REP-01 를 뺀 12문항 정확도를 함께 싣습니다.

| 넣은 정보 | 응답 정확도 | 논란 문항 제외 | 로그만 대비 (95% CI) | 2점 응답 | 잘못된 행동 | 첫 발화 p50 / p90 | 추정 적중 (0~2) |
|---|---|---|---|---|---|---|---|
| 로그만 | 91.1% | 100.0% | – | 25/28 | 0 | 875 / 1,210ms | – |
| 로그 + instant 추정 (v1 프롬프트) | 91.1% | 93.8% | +0.0%p (-14.3–19.6) | 24/28 | 0 | 927 / 1,490ms | 0.57 |
| 로그 + instant 추정 (v2 프롬프트) | 89.3% | 95.8% | -1.8%p (-12.5–8.9) | 24/28 | 0 | 955 / 1,390ms | 0.93 |

v2 추정 대 v1 추정: -1.8%p (-10.7–5.4). 참고: 같은 14문항의 기존 3회 반복 로그만 정확도 86.9% (논란 문항 제외 94.4%).

1. **추정은 나아졌지만 응답 정확도는 달라지지 않았습니다.** 추정 적중은 v1 0.57 → v2 0.93 으로 올랐지만, 응답에서 2점을 받은 수는 로그만 25/28, v1 24/28, v2 24/28 로 1건 안쪽 차이입니다(v2 대 v1 -1.8%p, -10.7~5.4).
2. **원인은 오를 여유가 없었기 때문입니다.** 정답 기준에 논란이 있는 QFR-02·REP-01 을 빼면, 이 실행에서 로그만 준 Mercury 3 medium 이 이미 100% 였습니다(기존 3회 반복 94.4%). 로그만 준 조건의 감점 3건은 모두 이 두 문항에서 나왔습니다. 추정이 응답을 바꿀 여지는 사실상 논란 문항에만 남아 있었습니다.
3. **추정이 응답을 해친 것으로 보이는 경우가 1건 있었습니다 (한 사례).** POL-02 "아 근데 그거 혹시 아직 취소되나"에서 v2 추정은 "아직 취소가 가능한지 물어볼 수 있다"고 주제를 정확히 맞혔습니다. 그런데 응답은 "네, 아직 취소 가능해요"라고 가능 여부만 답하고 취소하지 않아 0점을 받았습니다. 로그만 준 조건은 두 번 모두 2점이었습니다. 추정이 발화를 "질문"으로 적어 두면 문자적 해석을 거들 수 있다는 가설이 생기지만, 1건이라 확인되지 않았습니다. v1 추정 조건도 같은 문항에서 1번 같은 실수를 했습니다.
4. **첫 발화는 거의 그대로였습니다.** 로그만 875ms, v1 927ms, v2 955ms (p50) 입니다.
5. **정리.** Mercury 3 medium 은 로그만 줘도 논란 없는 문항을 거의 다 맞혀서, 이 문항들로는 추정의 응답 효과를 볼 수 없습니다. 효과를 보려면 3차에서 추정이 도움이 됐던 더 약한 응답 설정(Mercury 3 instant +7.8%p, GPT-6 Luna none +8.9%p)이나 더 어려운 문항이 필요합니다. 아래에서 Mercury 3 instant 와 GPT-6 Luna none 응답으로 시험했습니다.

#### 약한 응답 설정에 넣으면: Mercury 3 instant 응답 (24문항)

같은 v1·v2 추정을 Mercury 3 instant 응답에 넣었습니다. instant 는 3차에서 상위 모델 추정으로 +7.8%p 오른 설정이라 추정이 끼어들 여유가 있습니다. 로그만 준 조건과 같은 실행에서, v2 를 고칠 때 본 10문항과 못 본 14문항을 합친 24문항 × 3회입니다(3회째는 로그만 기준선의 흔들림을 줄이려고 따로 더 돌렸습니다). 추정 생성과 응답이 모두 Mercury 3 instant 이므로 상위 모델은 쓰지 않습니다.

같은 24문항의 기존 3회 반복 결과와 비교 (다른 시각 실행, 문항끼리 짝지음):

| 기존 조건 | 정확도 (논란 3문항 제외) | v2 추정 조건과의 차이 (95% CI) | 첫 발화 p50 (다른 실행) | 1,000턴당 비용 |

| Mercury 3 instant 로그만 | 84.0% (90.5%) | +5.6%p (-3.5–17.4) | 465ms | $0.07 |
| Mercury 3 instant 로그 + 상위 모델(Gemini 3.8 Flash) 추정 | 91.7% (93.7%) | -2.1%p (-11.1–6.9) | 477ms | $3.41 |

이번 v2 조건의 1,000턴당 비용은 추정 생성 $0.21 + 응답 $0.09 = $0.30 입니다(추정을 매 턴 만든다고 가정). 추정 생성 시간은 p50 1.1초, 최대 2.2초, 생성 실패 0/24 입니다. 기존 조건의 첫 발화와 비용은 30문항 × 3회 값입니다.

1. **v2 추정은 instant 응답의 정확도를 올렸지만, 효과의 크기는 +5.6~9.0%p 사이에서 불확실합니다.** 같은 실행의 로그만 대비 80.6 → 89.6% (+9.0%p, 0.7~18.8)로 신뢰구간 하한이 0 에 가깝습니다. 같은 24문항의 기존 3회 반복 로그만(84.0%) 대비로는 +5.6%p (−3.5~17.4)로 0 을 포함합니다. 첫 발화 p50 은 399 → 386ms 로 그대로였습니다. v1 추정도 +7.6%p (−1.4~17.4)로 v2 와 가깝습니다.
2. **3회째를 돌려도 이 실행의 로그만 기준선은 기존 값에 다가가지 않았습니다.** 같은 실행의 로그만은 2회까지 80.2%, 3회까지 80.6% 이고, 기존 3회 반복은 84.0% 입니다. 3회째에도 MUL-01 은 0점(3회 0·2·0점)이었고, 기존에 대부분 맞힌 POL-01 은 1·1·2점이었습니다. v2 조건은 2회까지 91.7% 에서 3회까지 89.6% 로 내려와, 같은 실행 대비 효과가 +11.5 → +9.0%p 로 줄었습니다.

3. **추정의 질도 나아지지 않았습니다.** 합친 목록의 추정 적중은 0.67 로 v2(0.75)보다 낮고, 관점별로는 0.58, 0.62 입니다. v2 를 고칠 때 본 10문항(0.40 vs 0.50)과 못 본 14문항(0.86 vs 0.93) 모두에서 v2 보다 낮습니다. 추정 수는 5.6개로 v2(3.9개)보다 많아졌습니다(문항당 글자 수 180 → 256).

   - 갈린 7문항(AMB-02, ELL-02, ELL-03, IMP-02, POL-02, REP-01, REP-03) 중 관점 B 가 정답에 다가간 것은 IMP-02 와 POL-02 뿐입니다. IMP-02 "내일 오전엔 팀 회의 있는데"에서 관점 B 는 "회의와 겹쳐서 치과 예약을 바꾸려 할 것"(적중 2점), 관점 A 는 "치과 예약을 그대로 확정할 것"(0점)이었습니다. 하지만 응답은 모든 조건에서 이미 2점이라 오를 여유가 없었습니다.
   - 합치면서 맞는 추정이 밀린 경우가 있었습니다. POL-02 에서 관점 B 의 취소 추정(0.7)이 관점 A 의 엉뚱한 추정(0.8) 아래로 가서, 관점 B 혼자는 1점이었던 적중이 합친 목록에서는 0점이 됐습니다. 두 관점의 확신도는 서로 맞춰져 있지 않습니다.
   - 관점 B 는 AMB-02 에서 기기 상태(집 거실)와 다르게 "사용자는 지금 회사에 있다"는 전제를 지어냈습니다(한 사례).
4. **Luna 의 되묻기는 로그만 수준으로 돌아왔지만, 정확도 차이는 가를 수 없습니다.** 채점 사유를 읽어 센 "의도는 맞히고 되물어 1점"은 로그만 5건, v2 9건, 관점 2개 4건입니다(경계 1건을 넣으면 5건). 논란 없는 문항만 보면 2 / 9 / 2건(경계 포함 3건)입니다. 물음표가 들어간 응답은 35 / 60 / 50% 입니다. 관점 A 가 "7시 반으로 예약을 확정할 것이다"처럼 실행하는 문장으로 추정을 써서 그랬을 수 있지만(가설), 바로 그 AMB-03 에서도 2회 중 1회는 되물었습니다. 앞 절에서 제안한 "실행할 의도로 쓴 추정" 조건을 일부만 건드린 결과라, 그 조건을 시험한 것으로 보지는 않습니다.
5. **비용과 생성 시간만 늘었고 첫 발화는 그대로였습니다.** 생성 비용은 호출이 둘이라 $0.21 → $0.39, 생성 시간 p50 은 늦은 쪽 기준 1.1 → 1.6초입니다. 같은 시각에 돌린 첫 발화 p50 은 instant 399 → 415ms(문항별 중앙값 −8ms)입니다. Luna 는 804 → 999ms 로 늘었고 v2 대비 문항별 중앙값도 +170ms 입니다. 그러나 로그만(851ms) 대비 문항별 중앙값은 −8ms 이고 p90 은 v2 가 더 길어(1,419 vs 1,221ms) 24회로는 판단하기 어렵습니다.
6. **정리.** 같은 생성기에 관점만 달리 주면 첫째 추정이 대부분 같아지고(17/24), 추정 개수만 늘었습니다. 관점이 서로 다른 추론을 끌어낼 것이라는 기대는 이 설정에서는 맞지 않았습니다. 다른 모델로 두 관점을 만들거나, 관점이 서로 겹치지 않게 강제하면 다를 수 있습니다(시험 안 함). v2 를 두 번 뽑아 합친 대조는 관점 조건이 v2 보다 나을 때만 돌리기로 미리 정했고, 낫지 않아 돌리지 않았습니다. 그래서 관점의 효과와 개수(5.6 vs 3.9개)의 효과는 나눌 수 없습니다.

### 여행 개인화와 관련도 게이트 (6차)

5차까지의 30문항은 사용자가 한 명뿐이라, 사용자의 목표나 기억에 따라 같은 말의 뜻이 갈리는지는 시험할 수 없었습니다. 그래서 여행 세트를 새로 만들어 세 가지를 시험했습니다.

- **목표·조건 목록:** 긴 활동 기록에서 사용자의 목표를 미리 정리해 두는 방식입니다(Pinterest 의 여정 추론, [원문](https://medium.com/pinterest-engineering/from-activity-to-intent-generating-user-journeys-with-llms-9652b9417626)).
- **여행 플래너 관점 추정:** 추정 생성기에 여행 플래너의 관점을 주는 방식입니다.
- **관련도 게이트:** 사용자가 말한 뒤 기억마다 관련도를 매겨 기준 이상만 넘기는 방식입니다(Jev, TypeSafe). 두 가지로 돌렸습니다. 게이트는 Jev 에 발화·기기 상태·직전 대화와 판단할 기억 1개만 주고, 맥락 게이트는 여기에 사용자 프로필과 기억 전체를 공통 상태로 더합니다. 두 경우 모두 질문은 기억 1개씩이고, 기준(0.4·0.5) 이상인 기억만 응답 모델에 넘깁니다.

**설계**

- 여행자 4명이 같은 주에 제주에 갑니다: 36개월 아이 동반 가족, 혼자 저예산, 출장, 신혼.
- 동행, 예산, 알레르기, 결제 규칙, 저장한 곳 같은 정보는 각자의 기억(최근 30일 활동 37~38개, 그중 24개는 일상 잡음)에만 있습니다. 기억을 먼저 고정 커밋한 뒤 발화와 정답을 썼습니다.
- 짝 8쌍(16문항)은 상태·직전 대화·발화가 같고 여행자만 다릅니다. 예를 들어 같은 "음 해산물이네"가 꽃게탕을 꼭 먹으려던 혼자 여행자에게는 수락이고, 아내가 갑각류 알레르기인 신혼부부에게는 거절입니다.
- 대조 4문항은 의도가 발화 안에 있어 기억이 필요 없습니다.
- 응답은 Mercury 3 instant, 20문항 × 2회입니다. 추정과 목표 목록도 Mercury 3 instant 가 만들고, 발화와 정답을 보지 않습니다.

2. **목표·조건 목록이 가장 높았지만, 미리 정한 비교(대 v2 추정)로는 가를 수 없습니다.** 짝 문항 87.5% 로, 기억 전체 대비 +14.1%p (1.6~29.7)이고 v2 추정 대비 +9.4%p (−4.7~21.9)입니다. 첫 발화는 그대로였습니다(같은 실행에서 468 → 428ms). 생성은 여행자마다 하루 한 번이라 비용이 거의 없습니다.
   - 일을 한 것은 목표가 아니라 조건 목록입니다. 목표는 여행자 3명이 "제주 여행 준비하기" 같은 1개뿐이었고, 결정적 기억이 표시된 15문항 중 14문항의 그 사실을 조건 목록이 담았습니다. 빠진 것은 B가 저장한 식당 하나입니다. Pinterest 원문에 없는, 제가 더한 부분입니다.
   - 이득 9점 중 4점이 P5-C 한 문항입니다. 출장자가 "이번엔 그 카드로 해 줘"라고 할 때, 기억을 모두 받은 응답은 두 번 다 개인 카드로 결제했습니다(규정은 법인카드). v2·플래너 추정도 이 문항을 똑같이 고쳤습니다.
   - 응답 표본의 흔들림만으로도 같은 크기의 차이가 났습니다(9번). 또 한 문항에 크게 기댑니다. P5-C 를 빼면 기억 전체 대비 +8.3%p (0.0~16.7)이고, 짝 문항을 하나씩 빼 보면 P5-C, P6-B, P6-D 중 하나만 빠져도 신뢰구간 하한이 0 이하가 됩니다. 미리 정한 비교도 아니었으므로, "조건 목록이 낫다"가 아니라 "그럴 가능성이 있다" 정도로 읽어야 합니다.
   - 대조 문항이 93.8 → 68.8% 로 떨어진 것은 CT-A 한 문항(−4점)입니다. "내일 아 아니 모레"를 정정 전 값인 내일로 설정했는데, 기억 없음 조건도 똑같이 틀렸습니다. 목표 목록 때문이라기보다 응답 모델이 이 문항에서 흔들린 것으로 봅니다(판단).
3. **여행 플래너 관점은 v2 추정과 같았습니다.** 짝 문항 −1.6%p (−12.5~9.4)입니다. 추정 적중은 1.05 대 0.95 로 조금 높았지만 응답은 달라지지 않았습니다. 5차의 관점 2개 실험과 같은 결론입니다.
4. **기억 1개만 보고 판단한 관련도 게이트는 정확도를 낮추고 첫 발화를 0.2초 늘렸습니다.**

## 왜 필요한가

- 사람의 대화는 차례 사이 간격이 평균 약 200ms 입니다. 음성 비서에서 언어 모델이 쓸 수 있는 시간은 그보다도 짧습니다.
- 음성에는 되돌리기 버튼이 없습니다. 한 번 오해하면 사용자가 다시 말해야 하고, 왕복 지연이 두 배 이상이 됩니다. 빠르지만 자주 틀리는 모델은 결과적으로 느립니다.
- 사람은 비서에게도 "난방 켜 줘" 대신 "아 좀 춥다"처럼 간접적으로 말합니다. 음성 인식 결과에는 억양과 문장부호도 없습니다.
- 정확도를 올리는 방법(추론 강도, 분석 서브에이전트)은 모두 지연을 늘립니다. 얼마를 내고 얼마를 얻는지는 모델마다 달라서 실측해야 합니다.

자세히: [왜 필요한가](docs/why.md)

## 화용론이란

같은 "아 좀 춥다"도 거실에서 음성 비서에게 하면 "난방 켜 줘"이고, 산책 중 친구에게 하면 "공감해 줘"입니다. 문장이 무엇을 뜻하는지(의미론)가 아니라 이 상황에서 이 말로 무엇을 하려는지를 다루는 분야가 화용론입니다. 간접 화행, 대화 함축, 전제, 직시·생략, 공손성·높임법, 반어, 대화 수정을 예시와 함께 정리했습니다.

자세히: [화용론 개요](docs/pragmatics.md)

## 실행 방법

```bash
uv venv .venv --python 3.12
uv pip install --python .venv/bin/python -r requirements.txt
```

API 키는 `.env` 에 넣습니다 (`.env.example` 참고, `.env` 는 git 에 올라가지 않습니다). 키를 클립보드에 복사한 뒤 아래 명령으로 넣을 수 있습니다. `K` 값만 바꿔 제공자별로 실행합니다.

```bash
F=.env; K=OPENAI_API_KEY; touch "$F"; sed -i '' "/^$K=/d" "$F"; printf '%s=%s\n' "$K" "$(pbpaste | tr -d '[:space:]')" >> "$F"; chmod 600 "$F"
```

```bash
.venv/bin/python -m vib.run --check          # 키 존재 여부만 확인
.venv/bin/python -m vib.run --arms all --reps 3
.venv/bin/python -m vib.judge                # 블라인드 채점 (claude-opus-5-5)
.venv/bin/python -m vib.report               # 표·차트 생성
```

키가 없는 모델은 건너뛰고 "미실행"으로 남습니다. 중단 후 같은 명령을 다시 실행하면 이어서 진행합니다. 파이프라인만 확인하려면 `--dry-run --out /tmp/vib-dry` 를 씁니다 (가짜 응답이며 `results/` 에는 쓰지 않습니다).

## 한계

30문항 규모, 한 사람이 작성한 정답, 텍스트 전용(실제 음성 인식·합성 없음), 도구 호출 없음, 측정 지역의 네트워크 지연 포함, A3·A4 프롬프트와 질의셋이 같은 분류 체계를 쓰는 점 등은 [실험 설계](docs/methodology.md#한계)에 정리했습니다.
