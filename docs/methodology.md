# 실험 설계

## 질문

음성 대화에서 사용자의 실제 의도를 맞히는 정확도를 올리려 할 때, 어떤 방법이 지연을 얼마나 늘리고 정확도를 얼마나 올리는가?

## 질의셋

`data/queries.json` 의 30개 문항. 각 문항은 다음을 가집니다.

| 필드 | 뜻 |
|---|---|
| `utterance` | 음성 인식 결과처럼 쓴 사용자 발화. 문장부호 없음, 군말("어", "음") 포함, 반말·존댓말 혼용 |
| `state` | 기기 상태(장소, 온도, 재생 중인 곡, 예약 등). 시스템 프롬프트에 "현재 상태"로 들어감 |
| `context` | 직전 대화 턴 (없을 수 있음) |
| `category` | 화용 현상 분류 13종 ([화용론 개요](pragmatics.md#이-리포의-분류표)) |
| `gold_intent` | 정답 의도 |
| `must` / `must_not` | 응답이 반드시 해야 할 것 / 하면 안 되는 것 |
| `clarify_ok` | 올바른 행동을 콕 집어 확인하는 질문도 정답으로 볼지 |

질의셋은 모델 호출 전에 고정했습니다. 실험 결과를 보고 문항이나 정답을 고치지 않습니다. 고친다면 버전을 올리고 전체를 다시 돌립니다.

## 조건

| 조건 | 내용 | 스트리밍 | 지연에 들어가는 것 |
|---|---|---|---|
| A0 effort 하향 (Mercury 3 만) | A1 에서 reasoning_effort 만 instant 로 낮춤 | 예 | 응답의 첫 텍스트 |
| A1 기본 | 각 모델의 음성용 기본 설정 | 예 | 응답의 첫 텍스트 |
| A2 effort 상향 | A1 에서 추론 강도만 한 단계 올림 | 예 | 추론 + 응답의 첫 텍스트 |
| A3 화용 서브에이전트 | 같은 모델이 A2 강도로 화용 분석 JSON 생성 → A1 설정 응답 모델이 분석을 받아 응답 | 분석: 아니오 / 응답: 예 | 분석 전체 + 응답의 첫 텍스트 |
| A4 화용 점검표 (요청 외 추가) | 별도 호출 없이 A1 시스템 프롬프트에 화용 점검표만 추가 | 예 | 응답의 첫 텍스트 |
| X 교차 A3 | 분석 모델과 응답 모델을 다른 제공자로 조합 (mercury→luna, luna→mercury) | 분석: 아니오 / 응답: 예 | 분석 전체 + 응답의 첫 텍스트 |

| C 공유 맥락 (2차) | 빠른 설정 + 시스템 프롬프트에 사용자 프로필(`data/profile.json`)과 문항별 최근 기록(`events`) | 예 | 응답의 첫 텍스트 |
| C+A4 맥락+점검표 (2차) | C 에 A4 의 화용 점검표를 함께 넣음 | 예 | 응답의 첫 텍스트 |

모델별 정확한 파라미터는 [모델별 설정과 출처](model-settings.md)에 있습니다.

## 2차 실험: 빠른 설정 + 화용 정보로 상위 모델에 얼마나 다가가는가

질문: 추론 강도가 낮거나 작은 모델에 화용 정보를 주면, **지연은 그대로 두고** 더 강한 모델의 정확도에 가까워지는가?

- 기준(빠른 설정 4개): Mercury 3 instant(A0), Mercury 3 기본(A1), GPT-6 Luna none(A1), Gemini 3.5 Flash-Lite minimal(A1). 비용 때문에 Haiku 는 넣지 않았습니다.
- 목표선(상위 모델): Gemini 3.8 Flash 기본 설정(A1). 1차 실험의 값을 그대로 씁니다.
- 방법: 추가 호출이 없는 것만 씁니다. A4(점검표, 1차), C(공유 맥락), C+A4(둘 다).
- **격차 해소율** = (방법 적용 후 정확도 − 기준 정확도) ÷ (목표선 정확도 − 기준 정확도). 정확도 변화는 같은 문항끼리 짝지어 구합니다.
- **지연 대조군**: C·C+A4 를 돌릴 때 기준 설정 4개를 같은 실행에서 다시 호출해 지연만 쟀습니다(`results/latency_control`, 채점하지 않음). 몇 시간 전에 잰 기준 지연과 비교하면 시간대에 따른 네트워크 차이가 섞이기 때문입니다. A4 는 1차 실험과 같은 시각에 잰 기준 지연과 비교합니다.
- **음성은 쓰지 않습니다.** 음성이 이미 인식되어 텍스트 메시지로 왔다고 가정합니다.
- **억양 표지 조건은 뺐습니다.** 처음에는 음성 분석기가 붙였다고 가정한 억양·발성 표지(한숨, 강세, 말끝 등) 조건도 설계했지만, 실제 서비스 메시지에는 이런 정보가 없습니다. 실제로 받을 수 없는 정보로 정확도가 오르면 서비스 판단을 오도하므로, 응답을 채점하기 전에 조건과 데이터를 지웠습니다.
- C 의 내용 원칙: 실제 시스템이 알 법한 사실(관계, 일정, 기기 기록, 재생 중인 곡 정보, 주문 상태)만 넣고, 말투나 의도에 대한 힌트("이 사용자는 돌려 말한다")는 넣지 않았습니다.

## 3차 실험: 맥락을 사람이 고르지 않으면

2차의 C 는 정답을 아는 작성자가 문항마다 관련 사실 1~2줄을 골라 넣었습니다. 실제 서비스에서는 이 고르기를 시스템이 해야 하므로, 사람의 선별을 빼고도 효과가 남는지 봅니다.

| 조건 | 맥락 | 사람이 고른 것 |
|---|---|---|
| C (2차) | 프로필 + 관련 사실 1~2줄 | 관련 사실 선택 |
| C-auto | 프로필 + 관련 사실을 관련 없는 기록 10개 사이 무작위 위치에 섞은 로그 | 없음 (잡음은 고정 시드로 무작위 추출) |
| C-auto+H | C-auto + 미리 계산된 추정 최대 5개 (확신도 포함, "사실이 아님" 표시) | 없음 |

- 대상: 2차에서 맥락 효과가 있던 빠른 설정 3개(Mercury 3 instant, Mercury 3 기본, GPT-6 Luna).
- 잡음 기록: `data/log_noise.json` 의 40개 중 문항마다 10개를 뽑습니다(`vib/build_auto_context.py`, 시드 20261027). 문항의 관련 사실과 충돌하지 않도록 난방·조명·알람 같은 기기와 문항 속 인물·예약은 피했습니다. 다만 김 대리의 메시지처럼 문항 인물과 겹치는 항목이 섞일 수 있고, 이것도 실제 로그의 잡음으로 둡니다.
- 자동 가설: Gemini 3.8 Flash(thinking MEDIUM)가 프로필·기기 상태·로그·직전 대화만 보고 "사용자가 지금 원하거나 신경 쓸 만한 것, 가리킬 만한 대상, 전제할 사실, 진행 중인 계획"을 추정합니다(`vib/hypothesize.py`). **사용자 발화와 정답은 보지 않습니다**(코드에서 확인). 사용자가 말하기 전, 턴 사이에 미리 계산한다는 가정이라 응답 지연에 넣지 않고, 문항당 한 번 생성해 `data/hypotheses.json` 으로 고정했습니다.
- 가설 생성기는 상위 모델(Gemini 3.8 Flash)입니다. 미리 계산하는 단계에서는 느린 모델을 써도 응답 속도와 무관하므로, "강한 모델의 추론을 오프라인으로, 빠른 모델은 응답만"이라는 구조를 시험하는 셈입니다.
- 지연 대조군은 실행마다 따로 보관합니다(`results/latency_control/context`, `results/latency_control/auto`).

A4 는 요청 범위 밖이지만, A3 의 정확도 향상이 "분석을 따로 하는 구조" 덕분인지 "화용 지식을 주입한 것" 덕분인지 가르기 위해 넣었습니다. A4 가 A3 와 비슷한 정확도를 내면 서브에이전트의 추가 지연은 필요 없다는 뜻입니다.

## 지표

- **의도 파악 정확도**: 채점 점수(0/1/2)의 평균을 2로 나눈 값. 문항별로 반복 평균을 낸 뒤 30문항 평균.
- **엄격 정확도**: 2점 비율.
- **95% 신뢰구간**: 문항 단위 부트스트랩 2000회.
- **첫 발화 지연** (`e2e_first_ms`): 요청을 보낸 시점부터 비어 있지 않은 첫 보이는 텍스트가 도착한 시점까지. 추론 토큰과 thinking 블록은 보이는 텍스트가 아니므로 이 시간 안에 들어갑니다. A3·X 는 분석 호출 전체 시간을 더합니다.
- **첫 문장 지연** (`e2e_sentence_ms`): 누적 텍스트에 처음으로 문장 끝 부호(. ! ? …)가 나온 시점. 음성 합성을 문장 단위로 시작하는 파이프라인의 지연에 가깝습니다.
- **분석 정확도** (A3·X): 분석 JSON 의 `intended_meaning`·`action` 이 정답 의도와 맞는지 별도 채점. 응답이 틀렸을 때 분석이 틀렸는지, 분석은 맞았는데 응답 모델이 못 따랐는지 가릅니다.
- **의도 이해율** (실행 후 추가한 보조 지표): 2점이거나, 1점이면서 채점 플래그가 "확인 질문함 + 문자적 해석·틀린 대상·과잉 행동 없음"인 비율. 의도는 맞히고 실행 전에 확인만 한 응답을 정답으로 봅니다. 실행 후 채점 결과를 보고 추가한 지표이므로 주 지표(의도 정확도)를 대체하지 않습니다.
- **A1 대비 변화**: 같은 문항끼리 짝지어(쌍체) 각 조건과 같은 응답 모델의 A1 의 차이를 구하고, 문항 단위 부트스트랩(2000회)으로 95% 신뢰구간을 냅니다. 모델 합산은 문항마다 모델별 차이를 평균한 뒤 문항 단위로 재표집합니다. Gemini 3.5 Flash-Lite A2(LOW)는 270회 모두 추론 토큰 0 이라 effort 가 실제로 오르지 않았으므로 effort 상향 합산에서 뺍니다 (`POOL_EXCLUDE`).
- **모델 간 비교**: 각 모델의 기본 설정을 Mercury 3 A1(공식 음성 가이드 설정)과 같은 방식으로 짝지어 비교합니다.
- **1,000턴당 비용**: 기록된 토큰 사용량 × 공식 가격(`vib/report.py` 의 `PRICES`). A3·X 는 분석 호출을 포함합니다. Gemini 는 추론 토큰이 `total - prompt` 로만 드러나 그 값을 출력으로 계산합니다.
- **평균 글자 수**, **마크다운 비율**: 음성용 출력 형식을 지켰는지 보조 지표. 마크다운 비율은 전 조건 0% 였습니다.
- 부트스트랩은 고정 시드와 정렬된 문항 순서를 써서, 같은 로그에서는 항상 같은 값이 나옵니다.

## 측정 절차

- 각 (조건, 문항)을 3회 반복합니다.
- 제공자마다 워밍업 호출 1회 후 측정을 시작합니다 (연결 수립 비용 제외).
- 같은 제공자 호출은 순차로, 다른 제공자끼리는 병렬 스레드로 돌립니다. 교차 조건(X)의 분석 호출은 응답 모델 쪽 스레드에서 나가므로 분석 제공자의 스레드와 동시에 호출될 수 있습니다.
- 문항마다 조건 순서를 돌려, 특정 조건이 특정 시간대에만 몰리지 않게 합니다.
- 오류가 나면 2초 뒤 한 번 재시도하고, 그래도 실패하면 오류로 기록합니다. 오류 행은 정확도·지연 계산에서 빠지고 표의 "오류" 열에 개수가 남습니다.

## 채점

- 채점 모델: `claude-opus-5-5` (effort low, JSON 스키마 강제 출력). 실험 대상이 아닌 상위 모델을 씁니다.
- 블라인드: 채점 모델은 조건 이름, 모델 이름, 지연을 보지 않습니다. 문항(상태, 맥락, 발화, 정답, must/must_not)과 응답 텍스트만 봅니다.
- 루브릭: 2 = 정답 의도 반영, must 전부 충족, must_not 위반 없음 / 1 = 방향은 맞지만 불완전하거나 불필요하게 되물음 / 0 = 오해, 문자적 의미로만 답함, 틀린 대상·값, 하지 말아야 할 행동.
- 채점 모델이 refusal 을 내면 다른 모델로 대체하지 않고 채점 오류로 남깁니다 (채점자가 섞이지 않도록).
- 채점 결과 일부를 사람이 직접 검수하고 그 결과를 README 에 적습니다.
- 실제 진행: 채점 도중 Anthropic 계정 사용 한도에 걸려 세 번에 나눠 채점했습니다. 같은 채점 모델·프롬프트·설정이며, 한도 오류로 실패한 행은 버리고 다시 채점했습니다. 한도 같은 복구 불가 오류를 만나면 채점기가 즉시 멈추도록 고쳤습니다.

## 한계

- **문항 수가 작습니다.** 30문항, 일부 분류는 1~2문항입니다. 분류별 수치는 경향으로만 읽어야 합니다.
- **정답은 한 사람이 작성했습니다.** 화용 해석에는 정답이 하나가 아닌 경우가 있어 `clarify_ok` 와 1점 구간으로 완충했지만, 작성자의 해석이 들어가 있습니다.
- **일부 문항의 정답 기준이 확인 질문에 지나치게 엄격합니다.** REP-01(치과 이름을 묻는 것), HON-01(문자로 보낼지 확인하는 것)처럼 빠진 정보를 묻거나 되돌리기 어려운 행동 전에 확인하는 응답이 1점이 됐습니다. QFR-02 는 "갈 수 있나"에 도착 가능 여부로 답한 응답을 길안내 제안이 없다는 이유로 0점 처리해, 함축 해석이 갈리는 문항입니다. 결과를 본 뒤 정답을 고치지 않았고, 대신 의도 이해율을 함께 보고합니다. 다음 버전에서는 "되돌리기 어려운 행동은 확인 허용"을 정답 기준에 명시하고, 함축이 논쟁적인 문항은 복수 정답으로 바꿔야 합니다.
- **비교가 많습니다.** 20개가 넘는 비교를 각각 95% 신뢰구간으로 보고하므로, 우연히 0 을 벗어나는 비교가 한두 개 나올 수 있습니다. 실제로 사실상 같은 설정(Gemini 3.5 Flash-Lite A1 과 A2, 둘 다 추론 토큰 0)의 차이가 −3.9%p (−8.3~0.0)로 경계에 걸렸습니다.
- **천장 효과.** 간접 요청, 전제, 음성 인식 오류는 거의 모든 조건이 100% 여서 방법 간 차이를 가르지 못합니다.
- **2차 실험의 맥락 기록은 정답을 아는 사람이 썼습니다.** 문항별 최근 기록(`events`)은 실제 시스템이 가질 법한 사실로 제한했지만, 어떤 사실을 넣을지는 정답을 아는 작성자가 골랐습니다(예: SAR-02 의 "현재 곡 장르 헤비메탈", QFR-02 의 "18:30 강남역 약속"). 실제 시스템의 기록은 이보다 잡음이 많을 수 있어, C 의 효과는 낙관적인 추정입니다.
- **목표선 모델에는 같은 맥락을 주지 않았습니다.** 2차 실험은 "빠른 설정 + 맥락"과 "상위 모델 기본 설정"을 비교합니다. 상위 모델도 맥락을 받으면 더 오를 수 있습니다.
- **A3·A4 프롬프트와 질의셋이 같은 분류 체계를 씁니다.** 분석 프롬프트와 점검표가 질의셋의 화용 현상 이름을 직접 다루므로, A3·A4 의 향상은 처음 보는 발화에서보다 낙관적으로 나올 수 있습니다. 예시 문장은 질의셋과 겹치지 않게 썼습니다. 일반화하려면 별도 검증 세트가 필요합니다.
- **채점 모델의 편향.** Anthropic 채점 모델이 같은 회사의 Haiku 응답을 후하게 볼 가능성을 배제할 수 없습니다.
- **텍스트 전용입니다.** 실제 음성 인식과 음성 합성은 없습니다. ASR 결과처럼 쓴 텍스트를 넣고, 첫 텍스트 시점을 음성 합성 시작 시점의 대리 지표로 씁니다.
- **도구 호출이 없습니다.** 비서가 "켰어요"라고 말하면 실행한 것으로 봅니다. 실제 도구 호출을 넣으면 지연과 정확도가 달라질 수 있습니다.
- **지연은 측정한 장소와 시간의 네트워크를 포함합니다.** 한국에서 각 제공자의 공개 API 로 호출한 값이며, 제공자 부하와 지역에 따라 달라집니다. 절댓값보다 같은 조건에서의 상대 비교로 읽어야 합니다.
- **A3 는 순차 실행입니다.** 분석이 끝나야 응답을 시작합니다. 실제 서비스에서는 짧은 맞장구를 먼저 말하는 동안 분석하거나, 분석과 응답을 추측 실행으로 겹쳐 지연을 숨길 수 있습니다. 이 리포의 A3 지연은 그런 최적화가 없는 상한입니다.

### 3차 결과 해석을 위한 확인

- **추정이 정답을 미리 담았는가**: 문항마다 추정 목록 전체를 분석 채점기(정답 의도와 대조, 0/1/2)로 채점했습니다(`results/judged/hypotheses.analysis.jsonl`). 정답 의도 명시 9개, 부분 포함 11개, 없음 10개였습니다.
- **미리 계산할 수 있었는가**: 직전 비서 발화가 있는 11개 문항은 비서가 말한 뒤에야 추정을 만들 수 있습니다. 추정 생성 시간(중앙값 7.6초, `results/latency_control/hypothesis_timing.json`)을 생각하면 실제로는 대개 늦으므로, 상태만으로 만들 수 있는 19개 문항의 효과를 따로 봅니다.
- 두 확인 모두 `results/hypothesis_checks.md` 로 다시 만들어집니다.
- **아직 재지 않은 것**: 추정이 틀렸을 때의 피해. 다른 문항의 추정을 넣는 대조 조건으로 잴 수 있습니다.

## 4차: 방법 후보 선별

[관련 연구](related-work.md)에서 뽑은 후보 6개를 싸게 걸러 내는 실험입니다.

- 응답 모델: Mercury 3 기본(A1) 하나. 맥락은 3차의 선별 없는 로그를 그대로 씁니다(M3 만 로그 대신 요약).
- 문항: 기존 3,330건 채점에서 2점 미만이 2건뿐이던 간접 요청·전제·음성 인식 오류 6문항을 빼고 24개. 반복 1회.
- 비교: 같은 24문항에 대한 기존 결과(Mercury 3 기본, 선별 없는 로그, 자동 가설 5개, Gemini 3.8 Flash, 각 3회 반복)와 문항끼리 짝지어 비교합니다. 지연은 같은 실행에서 다시 잰 Mercury 3 기본(24회)과 비교합니다.
- 발화 전 생성물(M1·M2·M3·M6)은 응답 실행 전에 `data/screen/` 에 고정했습니다. M1·M2·M3 생성기는 발화와 정답을 보지 않고, M6 은 발화 앞 절반(단어 기준, 올림)만 봅니다. 한 단어짜리 발화는 앞부분이 곧 전체입니다.
- M4 는 응답 모델이 `<해석> … </해석>` 안에 해석을 쓰고 그 뒤에 답합니다. 해석 부분은 들리지 않는다고 보고, 첫 발화는 `</해석>` 뒤 첫 글자가 도착한 시점입니다. 표지를 닫지 않으면 전부 들린 것으로 기록합니다(형식 실패).
- M5 는 M1 의 상황 10개를 후보로 주고, 실제 발화를 보고 "이 상황에 있는 사람이 이렇게 말했을까"로 하나를 고르게 합니다(RSA 의 청자 추론을 프롬프트로 옮긴 것). M1 과 입력은 같고 지시만 다릅니다.
- 추가 묶음(M7·M8·M5b·M5c)은 첫 묶음 뒤에 따로 실행했습니다. M7 은 M4 지시에서 해석 개수만 10개로 바꾸고 축과 형식은 그대로 둡니다. M8 은 같은 10개를 글로 쓰지 않고 속으로만 떠올리게 합니다. M5b·M5c 는 M5 의 고르기 지시는 그대로 두고 후보만 M2 목록(싼 생성기, 10개)과 M6 목록(말하는 중 빠른 생성기, 5개)으로 바꿉니다. 새 후보를 만들지 않고 이미 고정한 목록을 씁니다.
- 지연은 묶음마다 같은 실행에서 다시 잰 Mercury 3 기본(각 24회, 같은 스레드에서 조건 순서를 돌려 섞음)과 비교합니다(`results/screen/latency_control`, `latency_control_b2`). 표와 차트의 첫 발화 변화는 자기 묶음 대조군 대비입니다.
- 비용에는 생성기 호출 비용을 턴마다 더합니다. M5 는 M1 생성 비용을, M5b 는 M2, M5c 는 M6 생성 비용을 포함합니다.

- 한계: 1회 측정이라 문항 단위 잡음이 큽니다. 5%p 안쪽 차이는 판단에 쓰지 않습니다.

## 5차: 같은 모델 추정 (10문항 탐색)

- 질문: 추정을 응답 모델이 직접 만들면(Sleep-time Compute 논문처럼 같은 모델) 시간, 품질, 신뢰성이 어떤가. 함께 GPT-6 Luna effort none 과 low 의 지연 차이.
- 문항: 포화되지 않은 화용 범주 10개에서 1문항씩(파일 순서 첫 문항, 자기 수정은 논란 문항 REP-01 대신 REP-02). 반복 2회. 응답에 쓰는 추정은 1회째 생성물로 고정하고, 2회째에는 `--timing-out` 으로 생성 시간·실패만 다시 잽니다(`results/selfhyp/hyp_timing_rep2_*.json`).
- 추정 생성: `python -m vib.hypothesize --generator {mercury|luna} --items …`. 3차와 같은 프롬프트(`HYPOTHESIS_SYSTEM`)이고, 생성기 설정은 응답과 같습니다(Mercury 3 기본 = medium, Luna = low). 발화와 정답을 보지 않습니다. 오류나 형식 어긋남은 `failures` 에 남기고 최대 두 번 다시 시도합니다. 생성물은 `data/hypotheses_self/`.
- 응답: `python -m vib.run --selfhyp --reps 2 --items …`. 8개 조건(Luna none·low, Luna low 와 Mercury 3 기본 각각에 로그만·로그+Gemini 추정·로그+자기 추정)을 같은 실행에서 돌립니다. 제공자별 스레드 안에서 조건 순서를 돌려 섞습니다.
- 채점: 응답은 기존 채점기. 자기 추정 목록은 응답 행의 `analysis` 로 남겨, 화용 분석 채점기가 정답 의도를 담았는지 0~2점으로 채점합니다(3차 추정 적중 채점과 같은 기준).
- 신뢰성 정의: 추정 생성 실패(재시도 횟수), 추정 적중, 잘못된 행동(과잉 행동·대상/값 오류 플래그), 첫 발화 꼬리(p90·최대).
- instant 추정 조건(CI): 같은 추정 요청을 Mercury 3 instant 로 보내 만든 추정(`data/hypotheses_self/mercury_instant.json`)을 Mercury 3 medium 응답에 넣습니다. 생성 시간은 응답용 생성 10회와 시간만 다시 잰 10회(`--timing-out`)를 합칩니다.
- CI 는 앞선 조건들 뒤에 따로 실행했습니다. 첫 발화는 그 실행에서 함께 돌린 로그만·medium 자기 추정 조건(각 20회, 채점 안 함, `results/selfhyp/latency_control_ci/`)과 비교합니다. 응답 정확도는 앞서 채점한 로그만·자기 추정 결과와 같은 문항끼리 짝지어 비교합니다.
- 요약 표(`results/selfhyp/summary.md`)에서는 Gemini 3.8 Flash 추정 조건(CH)을 뺐습니다. 실행·채점 원본은 남아 있습니다.
- 한계: 10문항 × 2회라 응답 하나 차이가 5%p 입니다. 정확도는 방향만 보고, 시간·실패·비용을 주 결과로 봅니다. 중단된 첫 생성 시도(Mercury 2회 호출 중 1회 형식 실패, Luna 10회 모두 성공)는 파일에 남지 않아 README 본문에만 적었습니다.

### 5차 원인 분석 (추정 프롬프트 v1 대 v2)

- 질문: 추정의 질이 낮은 원인이 소스(생성기 입력) 부족인지, 생성 프롬프트인지.
- 잡음 추정 비율: 추정 문장에 로그 기록의 2글자 이상 낱말(일반 낱말 제외)이 나오면 그 기록을 쓴 것으로 보고, 관련 없는 기록만 쓴 추정의 비율을 셉니다(`vib/report.py` 의 `hyp_sources`). 근사치이며, 확인 과정에서 엉뚱한 기록이 함께 잡힌 경우가 있었습니다. 비교에는 같은 규칙을 고정해 씁니다.
- v2 프롬프트(`HYPOTHESIS_SYSTEM_V2`)는 v1 에서 관련성 기준과 0~5개 허용만 바꿨습니다. 본 10문항의 결과를 보고 고쳤으므로, 그 문항에서의 향상은 표본 안 결과입니다. 그래서 나머지 14개 비포화 문항에서 v1·v2 를 새로 만들어 비교했습니다(`results/selfhyp/diag/`).
- 추정 적중은 `python -m vib.judge --analysis-only` 로 한 번 채점합니다.
- 후속 시험: 못 본 14문항에서 v1·v2 추정을 Mercury 3 medium 응답에 넣고(`mercury.A1+CIv1`, `mercury.A1+CIv2`) 로그만(`mercury.A1+CA`)과 같은 실행에서 2회 돌렸습니다(`results/selfhyp/heldout/`). 추정 적중은 위에서 채점한 값을 쓰고 응답 행에서는 다시 채점하지 않습니다(`judge_hyps=False`).
